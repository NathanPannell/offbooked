# Offbooked

Remote line recording and run-through playback for theatre casts. A director uploads a script, shares one link per actor, each actor records their lines on their phone, and the server stitches everything into a lyrics-style run-through. The MVP backlog is in GitHub issues; #1 lists every credential and decision.

## Layout

- `backend/`: Node 24 + Fastify API and, later, the ffmpeg render worker. TypeScript runs through Node's type stripping, so there is no build step. `tsc` is for typechecking only.
- `web/`: the Vite + React app at offbooked.com (landing, director app, actor recording, run-through player, on-device accuracy check). See "Web" below.
- `web/ios/`: the iOS app, Capacitor 8 around the bundled web app (Swift Package Manager, bundle id `com.offbooked.app`), with native lock-screen playback, on-device take files and universal links. Built only on GitHub's macOS runners. See `docs/mobile.md`.
- `railway.json`: Railway build and health check config for the backend.
- `.github/workflows/`: `ci.yml` (the CI gate, see "Delivery"), `deploy-backend.yml` (deploys `main` to Railway), `ios.yml` (iOS simulator build, launch and screenshots on every PR into `main` touching `web/`; a TestFlight upload by hand or on `main`, skipped without the App Store Connect secrets).

## Delivery

Every change ships the same way, through the `deliver` skill (`~/.claude/skills/deliver/SKILL.md`). There are no preview deployments.

1. Branch from the latest `origin/staging` (`feat/`, `fix/`, `chore/` or `ci/<name>`), in the session's worktree or `<workspace>/.claude/worktrees/<branch>/`. Scratch files (logs, screenshots, throwaway databases) go in `<workspace>/.claude/tmp/<branch>/`, outside the repository, and can be deleted freely.
2. Open a **draft** PR against `staging`.
3. CI (`ci.yml`) runs only on PRs into `main` and pushes to `main` (owner's decision, 2026-10-24). For a PR into `staging`, run the same jobs locally; they are the gate there. The jobs:
   - **Backend**: `npm ci`, Prettier, ESLint with zero warnings, `tsc`, migrations applied twice to a throwaway Postgres 17 service container (the second run must be a no-op), and the tests with a coverage floor (`test:coverage`, which includes the render and retention workers' idle-no-queries tests). In CI the DB tests must run: `src/test/helpers.ts` fails without `DATABASE_URL`.
   - **Web**: `npm ci`, Prettier, ESLint with zero warnings, `tsc`, Vitest with a coverage floor (`vite.config.ts`), and the production build.
   - **E2E**: the web app built against a local API, served by `vite preview`, with the real backend on a throwaway Postgres (`web/playwright.config.ts`). The journeys in `web/e2e/` run on desktop and phone Chromium: a director signs in, uploads a script and copies the cast link; a cast member opens it, skips the intro, picks a part and reaches their lines. The report and traces are uploaded when it fails.
   - **Docker**: builds the Railway image, checks Piper speaks inside it and the aligner finds the line Piper said (`src/align/smoke.ts`).
   - **Security**: `npm audit --audit-level=high` for both packages, no committed `.env` files, and a gitleaks scan of the full history.
4. Review the diff, fix blocking findings, mark the PR ready once every local check is green on the head commit, and squash-merge into `staging`. Merging into `staging` deploys nothing.
5. Production is a separate PR from `staging` to `main`, made only when the user asks, gated by CI, and merged only with their approval. A push to `main` deploys the backend (`deploy-backend.yml`) and the web app (Vercel).

GitHub rulesets and branch protection need a paid plan for this private repo, so nothing stops a red PR from merging: merge only when every check is green on the head commit. Coverage floors are today's levels; raise them when coverage rises, never lower them. The backend floor counts only modules a test imports (Node's coverage), so give every new module a test. The React Compiler lint rules are off in `web/eslint.config.js` because the app doesn't use the compiler; the classic hook rules are errors.

Neon branches: the project (`mute-math-90372176`) keeps `production` (default) and `dev` (local development). A PR that needs its own Neon branch (say, to try a migration on real data) names it `dev-<head branch>`, lowercased, each run of characters other than a-z, 0-9 and - turned into one -, and no - at either end (`fix/smooth-staging` → `dev-fix-smooth-staging`), creates it with `expires_at` 7 days out, and gives it a 0.25 CU compute with the 300 s suspend timeout. `.github/workflows/neon-cleanup.yml` deletes that branch when the PR merges or closes (secret `NEON_API_KEY`, variable `NEON_PROJECT_ID`); it never touches `production`, `dev`, the default branch or a name not starting with `dev-`. Don't make Neon branches under any other name.

`/health` returns 503 when ffmpeg is not on `PATH`, so locally it is only 200 if ffmpeg is installed.

## Backend

- Contract: `docs/api.md`. Code: `src/routes/*` (HTTP), `src/parse/*` (file extraction, line labelling with Claude, cue repair, assembly), `src/render/*` (ffmpeg pipeline and in-process queue), `src/storage/*` (`local` or `s3`), `src/email/*` (Resend or log). SQL migrations live in `backend/migrations/NNN_name.sql` and run at startup.
- Scripts: `npm run dev` (loads `backend/.env`), `npm test` (DB tests run in a throwaway schema on `DATABASE_URL` and are skipped without it), `npm run typecheck`, `npm run seed` (demo director `director@example.test`, Hamlet 1.2, four actors, tone takes and a render; prints the sign-in link and invite URLs; `npm run seed -- --reset` archives the old demo and makes a new one).
- Env: `DATABASE_URL`, `SESSION_SECRET`, `INVITE_TOKEN_SECRET` (required); `APP_URL`, `API_URL` (base for local file URLs and the email unsubscribe and verification links), `CORS_ORIGINS` (comma list, `*` matches one host label); `ANTHROPIC_API_KEY` (optional; without it the heuristic parser is used); `EMAIL_DRIVER` (`log` or `resend`, defaults to `resend` when `RESEND_API_KEY` is set), `RESEND_API_KEY`, `EMAIL_FROM`; `STORAGE_DRIVER` (`local` with `STORAGE_DIR`, or `s3` with `S3_ENDPOINT`, `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`); `RENDER_DEBOUNCE_MS` (default 15000); `NORMALIZE_ON_UPLOAD` (default on; `0` normalizes takes on first use only); `TTS_DRIVER` (`piper` by default, `off` disables TTS), `PIPER_BIN` and `PIPER_VOICES_DIR` (default `/opt/piper/piper` and `/opt/piper/voices`, as in the Docker image), `TTS_CONCURRENCY` (clips synthesized at once, default 2; Piper keeps up to `TTS_CONCURRENCY` + 2 processes, one model each, and each holds 100–300 MB), `TTS_CUE_WAIT_MS` (default 2500); `ALIGN_DRIVER` (`wav2vec2` by default, `off` disables the aligner), `ALIGN_MODEL` (default `/opt/align/wav2vec2-base-960h-q4.onnx`, as in the Docker image; without the file takes are cut by loudness and have no word starts), `ALIGN_THREADS` (CPU threads per alignment, default 2); `PORT`, `APP_REVISION`.
- Script parsing (`src/parse/`) uses Claude Haiku only (`PARSE_MODEL = "claude-haiku-5-5"`, effort `medium`, in `src/parse/label.ts`). Never switch to a larger model. The flow:
  1. `source.ts` reads PDF (`pdf.ts`: reading order, overprinted/fake-bold text, kerning splits, running headers), DOCX (via HTML, so soft line breaks in verse survive) or plain text (UTF-8/16, Windows-1252). `noise.ts` strips line numbers that run through the document (`FTLN 0001`, margin counters).
  2. `label.ts`: Haiku labels numbered line ranges of about 180 lines (speech + speaker + cue, continuation, direction, heading, not-part-of-the-play). It never re-types text. `pipeline.ts` keeps each valid prefix and re-asks from the first unlabelled line, up to four times, before the heuristic parser takes the rest.
  3. `cues.ts` learns the cues used across the whole script and repairs the model's blocks: re-splits merged speeches at cue lines, fixes shifted speakers, claims cue lines labelled as directions, and reclaims dialogue labelled as front matter after the play has started.
  4. `assemble.ts` builds lines from the source text: strips cues, keeps each speech as one dialogue line with directions printed inside it or on its cue line (`[brackets]`, `_italics_` sentences, parentheses in scripts that use them for directions, ones the model marks with `>>`) left in its text as `[brackets]`, trusts printed act/scene headings over model numbers.
  5. Flags are computed but not stored or shown: the parser still works them out with the six codes in `flags.ts` (the model writes `?? <code>`; a speech that carries on after a direction or page break without a new cue is never flagged), but `saveStructure` in `job.ts` saves every line unflagged. There is no script review; migration `012_no_review.sql` cleared older flags.
- Parser changes must be measured with the benchmark in `backend/bench/` (README there). Run the training fixtures at least twice; model output varies between runs. Holdout sets live outside the repo in `<workspace>/.codex/holdout*` and are only for first-try checks. They are kept data, not scratch: never move them into `.claude/tmp/`.
- Neon ignores a plain `search_path` startup parameter; `createSql` passes it through `options` instead.
- Parts aren't owned (migration `014_open_parts.sql`). Anyone can pick any part, on the cast link or with "Record lines for another character", and record any line; picking a part (`actor_characters`, many actors per character) only says what someone means to record, so a cast member on a new phone just picks their part again. There is no unassigning and no `record-as`. Each part is labelled by its top recorder (`src/recorders.ts`: whoever recorded most of its lines among the takes that play now, plus a count of the others, "Robin + 2"), on the call sheet and the join cards.
- Audio sources: every dialogue line in a render uses its current take (the newest, by anyone: a cast member or the director), else a TTS clip, else silence. Timing entries carry `source` (`actor`, `director`, `tts`, `none`). A director's take is an ordinary take: progress, cast status, the call sheet, the actor-done email (once per cast member, whoever recorded their lines; `notifyActorsDone` runs after every take) and cast completion (every part someone picked is recorded) count every take; only TTS never counts. `voice_take(line, shared, voice)` picks a voice's current take. Every take in the API carries `recordedBy: { kind: "actor" | "director", name }` and `mine`. An actor's own `take` in `/api/invite/lines` is their latest own take; someone else's that plays is `current`.
- Takes: `src/takes.ts` handles both uploads (`PUT /api/invite/lines/:lineId/take` for actors, `PUT /api/lines/:id/take` for directors in `src/routes/studio.ts`), with the same idempotency and caps per recorder. Director takes (`recorded_by = 'director'`) have no `actor_id`; `recorded_by_user_id` holds the director. Normalizing a take cuts it to its speech (`src/render/trim.ts`): the noise floor and speech level come from the clip's own 10 ms frame levels, sound shorter than 40 ms (a tap or click) doesn't count, and the two ends are anchored on voiced sound (`voicing`: a 30 ms window at 8 kHz that repeats at a 60–400 Hz pitch after dipping at shorter lags, so rumble and pink room noise, which only fade with the lag, never count), so the breath before the line, the exhale after it, the breath for the next line in the auto-advance pause and bumps are cut; unvoiced sound joined to the first and last voiced part is kept (up to 300 ms before, 250 ms after: an "s" before the vowel, a final "t"), across a stop's closure (120 ms) when it is as loud as speech (the "s" of "Speak", "facts"), and, after the last voiced part, any sound within 12 dB of the speech level up to 300 ms on (a word said too fast to show its pitch; an exhale is quieter); then 250 ms before and after (`leadPadMs`/`tailPadMs`, 150 and 180 ms until `t7`); a take with nothing voiced (a whisper) is cut at its first and last sound. Nothing inside the speech is cut. When the server finds the line in the take (see the aligner below), the cut follows its words instead (`alignedBounds`): only the sound runs reaching within 200 ms of the line's words count, the edges are found on that voice as above, but never more than `onsetMs` (300 ms) before the first word or 400 ms past the end of the last word's letters, and never after the first word or before the last; then the pads. A cue read aloud before the line, an "um", a false start, a bump, or a scrape or an "Okay." after it never moves the cut. On two sets of hands-free fixtures (room noise, breaths, a bump, beats, fast and slow reads), with the old 150/180 ms pads: 98–100 ms kept before the first word and 143–170 ms after the last, mean, with no speech clipped (373–432 ms and 1,334–2,674 ms with the energy-only cut); about 0.25 s per 60 s take, 0.5 s for a 60 s whisper. Recordings then get a light clean-up (`highpass=f=70`, `afftdn=nr=10`, tracking the clip’s own noise floor; voices first, noise reduction second). Every clip, take or TTS, is normalized in two ffmpeg runs with one decode of the source (`normalizeClipCut`): the first decodes it once into the 48 kHz mono clip, cleaned up for recordings, kept as raw samples beside the output, and the 16 kHz copy the speech analysis reads; its integrated loudness over the cut is measured in-process (`render/loudness.ts`, BS.1770, within about 0.5 LU of loudnorm's), and the second run reads the raw samples, cuts them and applies one fixed gain to -16 LUFS (capped at ±30 dB) with a fast limiter at -1.5 dBFS, so all lines play at the same loudness (`level.test.ts`). The version is in the normalized key (`<take>.t8.flac`; t8: cut by the server's own word alignment), so older takes are redone lazily on first use; TTS clips move to `TTS_SETTINGS.version` 3 the same way. Takes have no real length cap (65 min server safety net, the app stops at an hour); one bigger than a request (8 MB) arrives in parts (`X-Take-Parts`/`X-Take-Part`), staged in the temp folder and joined into the original file (`stagePart`); the web uploader sends takes over 6 MB that way (`sendInParts`). The server trusts nothing the phone measured (owner's decision, 2026-10-25): an upload's `X-Word-Starts` header (the app's live tracker's word starts) is accepted, so older apps upload as before, and ignored: not stored (`takes.word_starts_ms` keeps what older takes had, unused) and not used for the cut or served. Each take is normalized as soon as it is uploaded (`normalizeSoon` in `render/takeaudio.ts`: one at a time, in upload order, at most 200 waiting, upload-driven only; `NORMALIZE_ON_UPLOAD=0` turns it off, as the test helper does unless a test asks), and normalizing finds the line's words in the recording itself (`src/align/`): a CTC speech model (`align/model.ts`: wav2vec2-base-960h, English letters, ONNX with its matrix products in 4 bits, 90 MB, run by `onnxruntime-node` on the CPU) gives each 20 ms frame's letter probabilities, and `align/ctc.ts` force-aligns the line's letters to them (Viterbi over the letters with blanks, the line's pieces from `linePieces`, which must stay in step with `lineTokens` in `web/src/player/words.ts`; numbers spelled out, [directions] not said). The line may start and end anywhere: frames outside it score as whatever the model heard best less a small penalty, so a cue read aloud before it, an "um", a false start or an "Okay." after it stay outside. A word fits when its frames score at most 1.5 nats a letter below the model's best there; the line is found when 55% of its words fit, else the take is cut by loudness (`speechBounds`) and served without word starts (the player spreads the words over `speech`). The starts (ms of the recording) are stored in `takes.aligned_word_starts_ms` and served moved by the cut. Measured on 62 two-voice SAPI takes with per-word truth (plain, beats, a cue read before, an "um" before, a restart, an "Okay." after; Opus like the phones send): word start error median 18 ms, p90 46, max 102; 218–298 ms kept before the first word and 249–357 after the last, nothing clipped, nothing extra kept. The staging pipeline on the same takes with the phone's starts late (its model loading, a slow phone) clipped up to 2.7 s of the line (17 of 62) and kept the cue, the restart or the "Okay." (19), and by loudness alone kept up to 4 s of them (40). Found: 96 of 97 clean takes (the miss: SAPI's fastest rate, which the model can't make out either), 45 of 60 under heavy room noise, echo and 24 kb/s Opus (their words still placed within 23 ms median), and none of 52 takes of another line or of no speech. Cost: about 0.2 s of one CPU per second of take (desktop), 0.9 s on 2 CPUs and 1.5 s on 1 for a 7 s take in the Docker image (model load included), 6.2 s and 11.6 s for a 49 s speech; the server holds about 300 MB more while the model is loaded (about 480 MB aligning a 50 s speech), and lets it go after a minute idle (a timer, never a query). The image is 135 MB bigger (the model and ONNX Runtime's linux/x64 library; the Dockerfile skips its CUDA download with `ONNXRUNTIME_NODE_INSTALL=skip`, CI too, and sets `ORT_DISABLE_TELEMETRY=1`). The aligner runs one take at a time on a `PriorityPool` (a line someone is waiting to hear before the upload queue). Whisper was not used: whisper.cpp tiny.en's DTW word times were measured further off than the live tracker's, and the teacher-forced Whisper check (#74) took 1.4 s per check on a desktop. CORS still allows `X-Word-Starts` and the part headers.
- Shared lines (`src/shared.ts`, migration `011_shared_lines.sql`): a character named after others ("ANGELO, ESCALUS") or after the company (ALL, BOTH…) is a group, never a part; its lines carry `voice_ids`. The SQL function `sync_shared_lines` recomputes groups and voices; every route that changes a production's characters or lines calls `afterCastChange`. ALL lines start with everyone who speaks in the scene (`voices_source = 'scene'`), then `inferEnsembleVoices` asks Claude Haiku (effort low, `ctx.ensemble`) per scene who is on stage (`model`); a director's pick (`director`) wins and is never recomputed. The view `line_voices` (one row per voice) and `voice_take(line, shared, voice)` (migration `014`) drive progress, the call sheet and playback: each voice's newest take by anyone (its `takes.character_id`, or an older actor take by someone who picked that voice). Two or more voice takes play as one mix (`render/mix.ts`, cached in `take_mixes` and storage by a hash of the takes). Takes are deleted by setting `deleted_at` (`setTakeDeleted`, which also moves `current_take_id` back); restore undoes it.
- TTS (`src/tts/`): Piper 1.2.0 (release `2023.11.14-2`) with `en_GB-cori-medium`, `en_GB-alan-medium` and `en_GB-vctk-medium` (16 English VCTK speakers), 18 voices in all, pinned with SHA-256 in the Dockerfile. `voices.ts` gives each character a voice from a hash of its id, in creation order, skipping voices already taken and never the narrator's (`NARRATOR_VOICE_ID`, VCTK p225, which reads stage directions in the run-through; bracketed directions inside dialogue are not read); title words in the name (QUEEN, LORD, LADY…) pick the gender. Lines are spoken by sentence, not by printed line (`spokenSentences` in `voices.ts`): the script's line breaks (verse, DOCX soft breaks, hard-wrapped prose) are joined with spaces, a word hyphenated across one is joined back, and each sentence (ending at . ! ? or an ellipsis before a capital, a digit or a quote, not after Mr. and the like) is one Piper utterance with a 150 ms gap after it; commas, colons, semicolons and dashes stay inside it. The displayed text keeps its breaks. Clips are keyed by a hash of (engine, model, speaker, spoken text, normalization settings), normalized like takes, stored at `tts/<hash>.flac` (and `.m4a` for cues) and recorded in `tts_clips`, so only changed lines are synthesized again. The spoken text in the key has the printed line breaks joined, so a line printed on one line kept its clip when speech went by sentence, and one that ran over several printed lines (about a third of a play's clips) was synthesized again as it was asked for. `piper.ts` keeps a pool of `piper --json-input` processes (one model each, idle ones exit after a minute), `TTS_CONCURRENCY` + models − 1 of them (`pooledProcs`, 4 by default) so every model keeps a loaded process: with fewer, alternating speakers on different models reload a model for nearly every line, which stalled run-throughs at a new scene in production. Never pass `speaker_id` to a single-speaker model; Piper aborts.
- Without Piper (Windows dev) the probe logs once, `/health` reports `tts: null` (it never fails health) and lines render as silence with `source: "none"`. To try TTS locally, unzip `piper_windows_amd64.zip` from the same Piper release, download the three voices (`.onnx` and `.onnx.json`) into one folder, and set `PIPER_BIN` and `PIPER_VOICES_DIR`. Tests never need Piper: `createTestApp({ synthesizer: new FakeSynthesizer() })` from `src/test/tts.ts`, and TTS is off by default in tests.
- Without the aligner's model (Windows dev) the server warns once and takes are cut by loudness, with no word starts. To try it locally, download `onnx/model_q4.onnx` from `Xenova/wav2vec2-base-960h` on Hugging Face at the Dockerfile's `ALIGN_REV` (check its `ALIGN_SHA256`) and set `ALIGN_MODEL`. Tests never need it: `createTestApp({ aligner: new FakeAligner(...) })` from `src/test/align.ts` (a fake model that hears given words at given times), and the aligner is off by default in tests.
- Cue audio: cues without a take get a TTS `.m4a`. `/api/invite` starts synthesizing the actor's cues in the background; the lines endpoints wait up to `TTS_CUE_WAIT_MS` for missing clips and return the rest with `audioUrl: null, audioSource: "none"` while they finish.
- Line-by-line playback (`src/linestream.ts`, `src/render/takeaudio.ts`): `GET …/lines/:lineId/audio` and `POST …/lines/audio/warm` (director and invite, see `docs/api.md`) return each line's own `.m4a`, so the player starts in about a second instead of waiting for the stitched render. Same source rules and cached files as the render: takes are normalized once into the FLAC the render uses plus a stream `.m4a` (`takes.stream_key`, one ffmpeg run), and every new TTS clip gets its `.m4a` (`cue_key`) beside its FLAC. `normalizeClip` reads clip lengths from the FLAC header instead of running ffprobe. A take playing alone (not a shared line's mix) also carries `speech` (stretches with voice in the served clip, from the trim's own frame levels, split on pauses of 150 ms+: `speechStretches` in `render/trim.ts`; stored at normalization in `takes.speech_ms` with the cut in `takes.trim_start_ms`, migration `016_take_timing.sql`; takes normalized earlier get both once in the background, `backfillTiming`: request-driven only, at most 2 at once (the rest wait for a later request), an upload ffmpeg can't read is never tried again, any other failure is retried by a request after 10 min) and `wordStartsMs` (the line's words as the server found them in the recording when the take was normalized, moved by the cut, dropped when the line's text no longer has that many pieces; absent when the line wasn't found). Neither is sent for TTS.
- TTS priority (`TTS_PRIORITY` in `src/tts/service.ts`): play > prefetch > cue > render, on a `PriorityPool`. Background work (cues, renders) gets at most `TTS_CONCURRENCY - 1` slots, so the stitched render runs one clip at a time with the default of 2; concurrent requests for one clip share one synthesis and raise its priority. Opening a run-through or asking for line audio prewarms Piper processes for the voices needed next (`prewarm`, only when the pool has room). Measured locally (Windows, warm Piper, render running): cold TTS line about 0.9–1.1 s to a playable URL, cached line about 0.17 s.
- The stitched render is built only when asked for (`POST /api/productions/:id/render`, and `npm run seed`): the run-through plays line by line and nothing in the app needs the one long file, so takes, deleting or restoring a take and opening the run-through no longer queue it (each used to re-stitch the whole script: about 70 ms a line with every take normalized, 2.5 s for a 36-line scene locally, every 2 minutes of recording and again on each stale open). The completion emails no longer wait for it: after every take, `notifyIfCastComplete` (`render/queue.ts`) sends them once every part someone picked is recorded. Staleness: the render content hash includes each line's TTS clip hash; `render.stale` still says when a built render is behind.
- Cast email verification (`src/email/verify.ts`, migration `015_actor_email_verification.sql`): `POST /api/invite/contact` keeps the address in `actors.pending_email` and emails a link signed like the unsubscribe link (HMAC with `SESSION_SECRET` over the actor, the address and the send time; valid 7 days, and only while that address is still the one waiting; the subject never names the production) to `GET /api/email/verify`. Opening it changes nothing, because mail scanners follow links: the plain HTML page has one "Confirm my email" button whose form POST moves the address to `email` and sets `email_verified_at`. An earlier unsubscribe stays unless that page said "confirming turns updates back on" (`resubscribe=1`). Asking with nothing to send (nothing waiting, or the verified address again) answers with the current state and `sent: false`. The invite page refetches `GET /api/invite` when it regains focus or visibility (no poll), so the profile catches a confirm in another tab. `email` holds only verified addresses: the migration marked every address already left as verified, and the director's legacy cast routes (unused by the web app) count theirs as verified. Only a verified email gets the run-through-ready email or keeps cast details through retention. Sends are rate limited (`verifySend` 5 an hour per cast member, `verifyTo` 5 a day per address, `verifyProduction` 20 an hour, `verifySendIp` 10 an hour per IP); the pages (`verifyOpen`, 30 per 15 minutes per IP) answer a limited request with a 429 "Too many tries" page, not JSON. `npm run seed` marks its demo emails verified. With `EMAIL_DRIVER=log` the response carries `devLink`, like sign-in.
- Performance dates and retention (`src/retention.ts`, migration `013_performance_dates.sql`): a production has `performance_starts_on` (optional) and `performance_ends_on` (always set: a new production without dates gets one year from today, a start alone is a one-night run; the migration gave every existing production 2027-10-20, or its old `performance_date` when later). The API exposes `performanceStartsOn`, `performanceEndsOn` and read-only `contentDeletesOn` (end + `RETENTION_DAYS`, 7); `performanceDates` in `routes/productions.ts` validates real dates, start ≤ end, and refuses a new final date more than 6 days ago (UTC), so a typo can't delete a show within hours; once content is due the final date is fixed (409 `content_due`). At 12:00 UTC on `contentDeletesOn`, `deleteProductionContent` archives the production, deletes `productions/<id>/` from storage (`Storage.deletePrefix`: takes, normalized and stream files, mixes, the script upload, renders), deletes the rows (scripts, sections, characters, lines, takes, renders, take mixes, practice runs, part assignments) in one transaction, sets `content_deleted_at`, then sweeps storage again for in-flight writes. It only touches a production that is due. Every writer under `productions/<id>/` (take upload, normalization, mix, render, script upload) calls `sweepIfDeleted` after its write, so anything that finishes after the deletion is swept and the writer stops; a script upload also takes the production row lock. **This is irreversible.** The row stays as a tombstone with its title; actor rows stay so cast and join links answer 410, but a cast member's name and phone are cleared unless they verified an email, and unverified addresses go for everyone (a director's own cast row is kept with their account); Synthesized speech goes too unless another production still uses it: clips are shared by hash, so `tts_clip_uses` (migration `018`) records which productions use each one (`TtsService.cached`/`ensure` with a production), and `tts/cleanup.ts` deletes, files and rows, every clip this production used, its lines' current hashes, any clip whose timings speak one of its printed lines (older engines and settings) and any clip without timings (from before settings version 3, which nothing can ask for), unless another production whose content is still there recorded a use (each clip's use is recorded as it lands, not at the end of a batch); the purge sweeps clips twice, before and after its transaction, and a clip made for it after the deletion is deleted as it lands. A render whose clip file has gone (another show with the same words took it) synthesizes it again (`prepareTts`). One gap: a clip made before `tts_clip_uses` existed for a line later edited matches nothing and stays. Productions whose director deleted their account answer 410 `production_deleted` on cast and join links, naming neither the show nor the director, and send no completion emails (`productionInfo` in `email/notify.ts`; a `@deleted.invalid` address is never written to). It is idempotent: a failure leaves `content_deleted_at` null for the next pass. Invite links expire at the same moment (`inviteExpiresAt`). The worker never polls: one query at startup (`dueContent`: what is due now and how long until the next), a timer to the next due time chained in memory past setTimeout's 24.8-day limit, a pass on every create or final-date change (`ctx.retention.kick()`), and catch-up alongside real `/api/` requests when a pass is overdue or failed (`touch`, at most once a minute). `/health` never reaches it. `retention.test.ts` has the idle-no-queries test.

- Live words and auto-advance on both recorders, the cast's and the director's part studio (options shared in `components/RecordOptions.tsx`; the studio's header has "Listen through" beside the title, headphones only on a phone, and "Back to cast") (`stt/live.ts` pure logic with tests, `stt/useLiveTake.ts`, `audio/liveCapture.ts`): an AudioWorklet (from a blob URL) downsamples the open mic to 16 kHz while a take records. Once the speech model is ready, the hook re-transcribes the take in the same worker (the whole take up to 10 s, then the last 7 s; less when passes are slow), pacing passes at 1.25 × the last pass's latency (350 ms to 2 s), and `applyPass` aligns each transcript with the line (free start, free end, skips, mishearings, repeats, contractions, numbers; `[bracketed]` directions are never required and show muted) to move a monotonic "spoken up to" cursor. The cursor traces along the line (`traceCursor`): a heard word moves it only when it is the next word or the one after (one missed), or up to 5 words on when the word after it is heard too, so a cue read aloud that shares a word with the line never lights the line up (with the gate, every correct take in the replay ends exactly when it did before). It follows the script, not the exact words: a word that sounds like the line's counts (`stt/sounds.ts`, a metaphone-style key with voiced/unvoiced pairs merged: "due" for "dew", "prayalty" for "frailty"; one word for two said quickly, "lesson" for "less than", only when each keeps a sound, so "king" is never "kin and"), and once the line's last words are heard (`tailHeard`: two of its last three, in order, the last among the newest two heard, only words found nowhere earlier in the line) the line is ended whatever was missed on the way. A pause in the voice (`PAUSE_PASS_MS`, 250 ms) starts a pass at once instead of at the next paced one, so the end of a line is transcribed as soon as the voice stops. An energy VAD with an adaptive floor drives `decideAdvance`: once there has been real speech, a pause always stops the take eventually, keeps it and moves on (and records the next line when "Keep recording" is on), so it never records forever (unless the wrong-line check flags it, see below); but it never ends a take on how long the actor has spoken (no expected line duration). The cursor sets the pause (`endPauseMs`, built from the take's state by `advanceInput`): 0.7 s once the end of the line is heard (every word, or its tail); 1 s one word from the end (`END_WORDS`, the last word is often missed), and also when a lagging transcript (a slow phone) is within three words of the end and the voice since the audio it heard is what those words take at the actor's own measured pace (`CATCH_UP_WORDS`; the words heard set the pace and how many are left, so speaking time alone never ends a take); 4.5 s when the transcript is current and the cursor sits at a comma or full stop partway through the line, or a word past one (`clauseBreaks`, `BEAT_SILENCE_MS`): a natural beat; 3 s when it is clearly mid-line elsewhere (heard words explain the speech); 2.5 s when the words weren't heard or the transcript lags, rather than guessing (passes keep running through the pause, so a transcript that catches up with the end moves on at once). Measured with the replay (`stt/replay.ts`, `liveReplay.test.ts`: 19 recorded fixture takes in `stt/fixtures/live-takes.json` with beats up to 4 s, mumbled and misheard words, fast and slow reads, each with the model's real passes at desktop speed and 3× and 5× slower): no false ends (6 before), and the take ends a median 736 ms after the last word at desktop speed, 1,059 ms at 3×, 1,594 ms at 5× (1,216, 1,274 and 1,766 ms before). A teacher-forced Whisper tiny.en end-of-line check ("did they say these next words?", `web/bench/live/whisper-endcheck.mjs`) was measured and not adopted: guided by the tracker's cursor it heard the end more often (31 against 23 of 38 moments, no false ends either way), but a check takes about 1.4 s on a desktop and 7 s at phone speed, so at phone speed it answers after the take has already ended, for another 44 MB (`docs/on-device-stt.md`). Wrong-line check (`flubbed` in `stt/live.ts`, `routes/actor/flub.ts`, `components/FlubPrompt.tsx`, both recorders): lenient, misspoken, swapped or paraphrased words are the line. When a take would end by itself in live mode, it is a flub only when under a third of the line's words were heard in any pass, or a nearby line (`nearbyLines`: its cue, the lines either side, the speaker's next line, the cue of the line after) was heard at least 60% (3+ words) and 0.3 more than this line, which was heard under 75%; a take no pass heard 3 words in is never judged. A flub doesn't move on or hand off: the take stops and is held, a soft chime plays on the mic's audio context (`MicSession.chime`), the card turns amber and asks "Did you mean to say something else?": ← "No, I'll read it again" (left, counts down 3 s and records the line again by itself, cue first with "Hear my scene partners"; a tap on either button ends the countdown) and ✓ "Yep, that's what I said" (right: keeps the take and carries on as hands-free would have). The same line flagged twice in a row waits for a tap. Recording anything else drops the held take. Never an offer to keep the take for another line. "Check I read the right line" in mic settings turns it off (`offbooked.checkLine`, on by default). Replay (`liveReplay.test.ts`, 26 correct takes incl. paraphrases and a cue read first, 7 flubs: only the cue, the next line, the line after, a wrong cue, nonsense; ×3 speeds): no false flags, every flub flagged, no flub lights more than one word; e2e `e2e/flub.spec.ts` plays a recorded flub through Chrome's fake mic (`--use-file-for-fake-audio-capture`) to the real model, cast and studio, desktop and phone. To re-record the fixtures (when the pass schedule or the model changes), see `web/bench/live/README.md`: SAPI voices speak the lines, ffmpeg adds room noise and breaths, and `record-passes.mjs` drives the app's worker through the dev server with Playwright. Without the model (first take, unsupported device) there's no highlighting and only a 2.5 s pause after real speech ends the take. "Go to the next line when I finish" (auto-advance) and "Keep recording the next line" are in mic settings, both on by default so recording is hands-free, stored in localStorage only once chosen (`offbooked.autoAdvance`, `offbooked.recordNext`; the old `offbooked.keepRecording` is ignored, so a "0" left by someone trying the switch while it was off by default doesn't keep them off). "Keep recording" only chains takes while the speech model follows the words (live mode), never on the mic level alone. Chaining is a handoff with no gap (`handoff` in `audio/useTakeRecorder.ts`): the next line's MediaRecorder starts on the same open mic and the finished one stops only on the new one's `start` event (`overlapTakes`, `ActiveTake.started`), so the takes overlap by a few ms and nothing said between them is lost; the live capture starts the next take on the next frame (each take is a generation, so the old take's flushed block never lands in the new one). Blob assembly, the IndexedDB queue, scoring and the card's "Saving…" state (`finishing` on `LineCard`) all happen in the background, and the after-take scroll runs once the kept take's bar has rendered. Measured locally (desktop Chromium, fake mic): 65 ms from the end of one take to the next recording, 0 ms of audio lost (it was 930 ms, all lost). Into a line whose cue plays first ("Hear my scene partners"), the take stops and the cue starts at once; the take still waits for the cue's end plus `CUE_SETTLE_MS`. A take that stops without chaining still waits 700 ms (600 in the studio) before moving to the next line. Measured on a desktop CPU with Moonshine tiny: 60–300 ms per pass for 1–4 s of audio, 500–880 ms at 7–10 s; each take logs `[live stt] n passes, median, max` with `console.debug`. While a take records, the next word to say is followed karaoke style (`useFollowWhileRecording` in `routes/actor/recorderFollow.ts`, `keepInView` underneath): held near the middle of the band, never so low that fewer than three rows show beneath it (the run-through follows the same rule), from the take's first word, as the cursor moves, or without the model at an average reading pace from the speech time (`paced`, 300 ms voiced per word; it only scrolls, it never ends a take). LineCard's word spans carry their tokens (`data-tok-start`, `data-tok-end`) while a take records. The cast recorder's band is `recorderBand` (pinned `.record-header` to the dock); the studio's header isn't pinned, so it uses `studioBand` (the app's pinned `.app-header` to the dock), also for the scroll after a take (`revealAfterTakeIn`). A scroll by hand pauses it for 2.5 s. The phone measures no word timing for the server (the server finds each take's words itself and ignores `X-Word-Starts`; the app no longer sends it): `stt/wordTiming.ts` only keeps the take's voiced stretches and when the end of the line was heard, for where Listen back stops (`listenEndMs`). The capture keeps only the last 30 s of samples, so long takes stay small. An actor with several parts records one at a time: chips under the header switch parts (`offbooked.part.<token>`), picking up a part shows it, and the run-through opens on that part (`?part=`).
- Playback speed (`audio/speed.ts`, `components/SpeedButton.tsx`): one speed for every player, 0.5×, 0.75×, 1× (default), 1.25×, 1.5×, 2×, 3×, 4×, a small button showing it that steps to the next on a tap (round again after 4×), remembered on the device (`offbooked.playbackSpeed`) and kept in step across buttons and tabs. It sits in the run-through's player bar (other people's lines) and beside Listen back on every take in both recorders (`usePlayback`: takes, Play together, cue previews; a change applies to what is playing). `applySpeed` sets `playbackRate` and `defaultPlaybackRate` (a new src resets to it, so every next clip keeps the speed) with `preservesPitch` (and the `webkit`/`moz` names). Gaps, my-line pauses, the cue before a take, the accompaniment while recording and the mic check stay at 1×.
- `web/vercel.json` rewrites every non-asset path to `index.html`. The mic is only requested from a record tap, never on load.

## Product rules that shape the code

- Actor invite links are shared by the director (copy link or the native share sheet). The app does not email or text invites or reminders.
- Email (Resend) is only for completion notifications (an actor finished all their lines, the cast is complete, the run-through is ready) and the verification link a cast member asks for in their profile. Only a verified cast email gets the run-through-ready email.
- Every production has performance dates. Its script content and recordings (every take, re-records and deleted takes included, renders, the uploaded script and all parsed lines) are deleted for good 7 days after the final performance, by the retention job (see Backend). Cast details go with them unless they are tied to a verified email: names and phones of cast members who verified no email are cleared, and so is every address still waiting for its verification link. Nothing else deletes audio: re-records keep older takes, deleting a take only hides it (`deleted_at`, restorable), and archiving deletes nothing until that date.
- The cast never sees the director's email. Anything that names the director to the cast goes through `castFacingName` (`backend/src/names.ts`): their name, else the part of their email before the @, capitalised.
- Actors have no accounts. Their invite token is their only credential and is scoped to their own lines plus cue context.
